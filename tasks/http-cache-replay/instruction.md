A company runs a shared HTTP cache, similar to a CDN edge node or a reverse proxy, that sits in front of a single origin server and serves many different clients. They have kept a log of every request that clients sent to this cache, and they now need to know exactly what a correct shared cache would have done with each one. Your job is to replay that log and work out, request by request, how a shared cache that conforms to RFC 9111 (HTTP Caching) would have behaved.

The log is in /app/data/requests.jsonl. It holds one JSON object per line, and the lines are in the order in which the requests reached the cache. The cache handles them one after another, so whatever it stores while handling one request is still there for the requests that follow. Every object has a request_id, a received_at field giving the moment the request reached the cache in whole seconds on the cache's own clock, the request's method and url, and a headers object holding the request headers. Each line also has an origin object describing the response the origin server sends if the cache contacts it while handling that request. That object gives the response status, the response headers, and its own received_at, which is the moment the cache received that response, measured on the same clock as the request's received_at. The origin object is present on every line, whether or not the cache needs to contact the origin for that request. Header names are case-insensitive, as they are in HTTP, and any dates in header values use the standard HTTP date format.

RFC 9111 leaves some choices up to the person building the cache, so make the following assumptions. The cache has unlimited storage and never evicts or throws away anything by itself. The origin is always reachable, and whenever the cache contacts it while handling a request, it replies with exactly the response given in that line's origin object. Only responses to GET requests are ever stored. When a response has no explicit freshness lifetime but the standard allows the cache to use a heuristic one, the heuristic lifetime is ten percent of the time between the response's Date and its Last-Modified value. The received_at values are the cache's only source of the current time. The Date headers were written by the origin's clock, which is a separate clock from the cache's.

For every request in the log, decide what the cache does with it, whether it stores the response it gets from the origin, and what Age value it sends to the client along with the response. Base each decision on what the standard requires or allows a shared cache to do, together with the assumptions above.

Write your results to /app/output/decisions.csv. The first line must be exactly the header request_id,action,stored,age. After that, write one row for every request in the input, in the same order as the input, with no requests left out and none repeated. The action column holds one of three values. HIT means the cache answered from a stored response without contacting the origin at all. REVALIDATED means the cache had a stored response but checked it with the origin before answering. MISS means the cache fetched the response from the origin instead of using a stored one. The stored column is true if the cache stored a new response or updated a stored one while handling that request, and false otherwise; write both values in lowercase. The age column is the Age value that the cache sends to the client with its response, written as a whole number of seconds.

Your output will be compared row by row with the behaviour of a correct shared cache, so every column of every row counts. The file should contain only the header and the data rows, with no extra columns, comments or blank lines.

You have 28800 seconds to complete this task. Do not cheat by using online solutions or hints specific to this task.
